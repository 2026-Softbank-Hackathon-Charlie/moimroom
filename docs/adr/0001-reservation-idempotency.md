# 0001. 예약과 멱등 재시도 영수증을 같은 PostgreSQL 트랜잭션에 저장한다

- 상태: 채택
- 날짜: 2026-11-06
- 관련: platform #91, migration-engine #19

## 상황

예약 생성 commit 후 응답 연결이 끊기면 클라이언트는 결과를 모른다. 기존 슬롯 PK는 두 예약을 막지만 같은 요청의 원래 예약 코드를 돌려주지 못한다.

## 결정

POST /api/reservations에 선택적인 Idempotency-Key를 지원한다. 키는 16~128자의 공백 없는 ASCII이며 클라이언트는 요청마다 충분히 무작위인 새 키를 만들고, 결과 불명 때 같은 키·같은 의미의 요청으로 재시도한다. 같은 키·같은 요청은 최초 201 결과를 돌려주고 다른 요청은 409 idempotency_key_reused이다. 키 없는 기존 동작은 유지한다.

예약·슬롯과 app.reservation_retries 영수증을 동일 트랜잭션으로 저장한다. 키의 PK와 행 잠금으로 동시 요청을 직렬화하고 commit 응답이 불명확해도 다음 재시도가 commit 여부를 확인한다. 실패 트랜잭션은 영수증도 남기지 않는다. 성공 영수증은 현재 예약 조회가 아닌 최초 결과 snapshot이므로 이후 취소되어도 동일한 원래 응답을 반환한다. 최신 상태는 lookup API로 확인한다.

키는 endpoint와 함께 SHA-256으로 저장한다. 정규화 요청에는 전화번호가 있으므로 빠른 평문 hash를 저장하지 않고 기존 전화번호 저장과 동일한 무작위 salt/PBKDF2-SHA256 100,000회 형식을 사용한다. 원문 키/전화번호/요청은 새 테이블에 보관하거나 로그에 남기지 않는다. 응답 snapshot에는 기존 API와 같은 이름·전화 뒤 4자리가 포함되므로 기존 예약 데이터와 같은 접근·보존 정책이 필요하다.

## 검토한 대안

- 메모리 캐시: 앱 재시작과 환경 이전을 견디지 못한다.
- 게이트웨이 재전송만 도입: DB commit 여부를 알 수 없다.
- 별도 commit의 영수증: 예약 commit과 영수증 사이 장애가 중복 재실행을 만들 수 있다.
- 단순 요청 SHA-256: 전화번호 등 저엔트로피 개인정보 사전 대입 비용이 낮아 기각했다.

## 결과

스키마 추가는 IF NOT EXISTS이며 기존 앱이 계속 읽을 수 있다. 하지만 키를 무시하는 옛 바이너리로 복귀하면 재시도 보장은 사라진다. 이전/복귀 양쪽 앱이 이 계약을 지원하고 ledger 테이블을 물리 복제/백업에 포함해야 한다. ledger는 자동 삭제하지 않는다. 보장할 retry/rollback window 동안 보존하고 오래된 키를 재사용하지 않는다. 보존·삭제 정책과 저장 용량은 운영 적용 전에 결정해야 한다.

동일 키 요청은 원격 DB 잠금과 PBKDF2 계산을 기다릴 수 있으며 취소/DB 오류는 결과 불명으로 취급하고 같은 키로 재확인한다. 이 기능은 새 primary 환경 유실의 RPO=0이나 외부 결제·이메일의 exactly-once를 보장하지 않는다. 취소·후기·파일 업로드 endpoint에는 적용하지 않는다. 운영 배포는 별도 작업이다.
